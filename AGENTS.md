# SPR Note — Enterprise Engineering Guidelines

## Core Principles

1. **Zero Hardcoded Logic:** Never hardcode conditional colors, categories, types, or labels using inline `if-else` / ternary branches (e.g. `isHoliday ? "rose" : "amber"`). All taxonomy items and styling must be driven dynamically by their source schemas and stores.
2. **Enriched Presets:** All dropdown options must encapsulate their full metadata (`type`, `category`, `color`, `repeats`, `description`, etc.) at creation time so handlers consume them cleanly.
3. **Enterprise UI Consistency:** Use project design tokens only. No hardcoded colors or raw styles. Ensure seamless dynamic sync between Developer Tools and all application views.
4. **Clean & Reusable Codebase:** Maintain high code quality, clear comments, and robust enterprise scalability across all modules.
5. **Right Sidebar / Drawer Container Responsiveness:**
   - **Never use Viewport Queries (`sm:`, `md:`) for internal drawer grids:** Viewport queries query `window.innerWidth`, which mistakenly forces 2 cramped columns on desktop even when the sidebar width is narrow (360px - 480px).
   - **Always use Container Queries:** Use `@container` and `@[480px]:grid-cols-2` (or `@[460px]:grid-cols-2`) for all multi-field rows inside right sidebar forms and drawers. This ensures automatic 1-column layout on mobile or narrow widths and seamless 2-column layout when the sidebar is wide (>= 480px) or resized.
   - **Zero Double-Padding:** Set `padding="none"` on `DrawerContainer` inside `RightSidebarPanel` since the sidebar panel already provides container-level padding.
   - **Streamlined Section Separation (Zero Boxed Cards):** All right sidebar drawer forms must group inputs into clean, distinct logical sections (e.g. `Campus Information`, `Location Details`, `Leadership & Contact`) using streamlined section headers (`flex items-center gap-2 pb-2 border-b theme-border`) with proper top and vertical breathing space (`space-y-6 pt-2`), avoiding redundant nested card backgrounds/borders (`DrawerSection` card wrappers).
   - **Complementary Field Pairing:** Complementary fields (e.g. Category & Sequence, Start & End Time, Department & Target Class, Section Scope & Target Section) must share a container-responsive row (`@[480px]:grid-cols-2`).
   - **Unique Form Keys:** Always pass unique dynamic `key` props to form components inside drawer registrations to ensure pristine mounting and state initialization across Add and Edit modes.
6. **Mandatory TypeScript for All New Features & Files:**
   - **TypeScript Default:** All new features, components, modules, submodules, stores, hooks, and utilities must be created in TypeScript (`.tsx` and `.ts`).
   - **Explicit Type Interfaces:** Every component and module must define and export explicit TypeScript interfaces and type definitions (e.g. `types.ts` or colocated exported interfaces).
   - **Strict Type Safety:** Ensure zero runtime type ambiguity and strict type safety across all frontend workflows to guarantee seamless mobile app code-sharing and native Android compilation (Capacitor / React Native).
   - **Progressive Migration:** Existing legacy `.jsx`/`.js` files should be progressively converted to `.tsx`/`.ts` during feature updates.
7. **Mandatory 4-Language Localization (i18n & l10n) and Bidirectional (RTL) Standard:**
   - **Core 4-Language Matrix:** All new features, screens, tables, forms, modals, drawers, alerts, buttons, and navigation elements must support a minimum of 4 languages:
     1. `en` (English) — Default primary application language.
     2. `bn` (Bengali) — বাংলা.
     3. `ar` (Arabic) — العربية (Right-to-Left bidirectional layout).
     4. `ur` (Urdu) — اردو (Right-to-Left bidirectional layout with Nastaliq line-height handling).
   - **100% Pure English Codebase & Default Fallback:** The core codebase, JSX/TSX markup, state identifiers, backend models, logs, and default fallback parameters must strictly remain 100% pure English. Never hardcode Bengali, Arabic, or Urdu strings directly inside component logic or templates.
   - **Colocated Module-Level Translation Dictionaries (Self-Contained Localization):**
     - All module-specific translation dictionaries must reside directly inside the respective module's own folder under `<module-path>/locales/{en, bn, ar, ur}.ts` and an `index.ts` barrel registering them via `registerModuleLocales(namespace, { en, bn, ar, ur })`.
     - The global `frontend/src/i18n/locales/{en, bn, ar, ur}/` is strictly reserved for application-wide, cross-cutting namespaces (such as `common`, `navigation`, `settings`, `errors`).
     - Feature-specific keys must never bloat the global dictionary files. When creating or updating any module, translation keys must be maintained across all 4 locales (`en`, `bn`, `ar`, `ur`) inside that module's own `locales/` directory.
   - **Universal `useTranslation` Hook Usage:** Always consume translations using `const { t, formatNumber, formatDate, isRTL } = useTranslation(namespace);` with standard fallback chaining: `t('key', 'Default English Text', params)`.
   - **Bidirectional RTL Compliance:** Every UI layout, flex arrangement, text alignment, and icon orientation must seamlessly adapt to RTL mode when Arabic or Urdu is active (using `rtl:...`, CSS logical properties, or text alignment tokens).
   - **Intl Number & Date Formatting:** All displayed numbers, dates, and times must pass through centralized formatters (`formatNumber`, `formatDate`, `formatTime`) to ensure culturally accurate numeral rendering across Bengali (`১, ২, ৩`) and standard/Arabic formats.
8. **Large Feature & Module Decomposition Standard (Strict Modular Architecture):**
   - **File Size Threshold:** No single view/component file should become overly large or monolithic (>300-400 lines). When a feature or screen grows complex, it must be proactively decomposed into dedicated subfolders and single-responsibility modules.
   - **Standard Modular Directory Structure:**
     - `MainView.tsx` — Lean, readable high-level orchestrator focusing exclusively on layout composition, top-level state wiring, and coordination.
     - `components/` — Dedicated subfolder for all specialized UI blocks, sub-components, table cell editors, action toolbars, and feature-specific modals (with a clean `index.ts` barrel export).
     - `hooks/` — Dedicated subfolder for isolated custom hooks managing filter scopes, cascading state, column configurations, metric builders, and complex grid/form operations (with a clean `index.ts` barrel export).
     - `types.ts` — Shared interfaces, parameter contracts, and action types.
     - `index.ts` — Centralized module-level barrel re-exporting views, sub-components, and hooks cleanly.
   - **Zero Logic Bloat in Views:** Keep view files focused on orchestration by delegating heavy business logic, column constructions, and modal bodies to their respective subfolders.
9. **Root-Cause First Resolution Standard (সমস্ত সমস্যার রুট কারণ বের করে স্থায়ী সমাধান):**
   - **Zero Superficial Workarounds:** Whenever any bug, discrepancy, sync failure, or UI glitch is encountered, never mask symptoms with superficial patches, ad-hoc state overwrites, or blind timeouts. Always trace the entire data pipeline across PostgreSQL schemas, Django REST serializers, sync engine queues, IndexedDB repositories, and React component lifecycles to find and resolve the genuine root cause.
   - **Architectural Permanence:** Every fix must be architecturally solid, thoroughly tested across cold starts and online/offline transitions, and documented with clear rationale in project guidelines to ensure it can never recur.
10. **Single Source of Truth for Data Calculation & Metric Aggregation (একক প্রামাণ্য ডাটা ক্যালকুলেশন নীতি):**
   - **Zero Fragmented Calculations:** Never calculate, parse, count, or aggregate business data independently across different UI components, table column renderers, card grids, export handlers, or analytics engines. All business metrics, counts, and summaries (e.g. mistakes, stucks, pages recited, attendance counts, financial totals) must be computed in a centralized, authoritative domain resolver module (e.g. `studentMetaResolver.ts` or designated domain utility).
   - **Universal Consumption Across All Presentation Layers:** Every view layer—parent table rows, collapsed summary badges, expanded child details, grouped rollups, card grids, and analytics dashboards—must strictly consume the exact same canonical resolver function. If calculation logic evolves or changes, updating the single resolver must instantly and automatically update all views synchronously.
   - **Performance, Purity & Ingestion Memoization:** All canonical domain resolvers must be pure functions with deterministic outputs. For high-volume collections, datasets, and virtualized tables (500+ items), expensive multi-pass parsing must be executed once during data normalization/ingestion (`normalizeReport` / `useMemo`) and exposed via $O(1)$ pre-computed properties rather than repeatedly executing iterative loops inside high-frequency cell render cycles.
   - **Backend & Serializer Alignment:** Backend Django REST serializers must mirror the Single Source of Truth by deriving aggregated metrics directly from canonical relational child records (using `SerializerMethodField` or domain managers) to guarantee that server payloads, offline IndexedDB caches, and client views remain 100% mathematically identical.
   - **Single Point of Integrity:** Data calculations must never be duplicated. If an error or fix occurs, it must occur uniformly across every screen; no view may ever display divergent numbers for the same underlying record.
11. **Multi-Tenant Isolation & Zero Data Leakage (মাল্টি-টেন্যান্ট আইসোলেশন ও ডাটা সুরক্ষা নীতি):**
   - **Strict Tenant-Scoped Storage Keys:** All client-side storage keys (`localStorage`, `sessionStorage`, `IndexedDB`), cache entries, and draft repositories must strictly prepend the active tenant/institution identifier (e.g. `spr_reports_local_<tenant_id>_v1`, `spr_students_cache_<tenant_id>`). Never write or read un-scoped, global persistent cache keys.
   - **Pristine Context Switching:** When a user switches campuses, academies, or tenant organizations, all tenant-scoped in-memory stores, lookup maps, and active view states must immediately reset or re-initialize from that tenant's isolated cache to prevent cross-organization data contamination.
   - **Backend Scoping & Defense-in-Depth:** Every Django REST query and mutation must enforce strict organization filtering based on the authenticated request context (e.g. `tenant_id` from JWT / active membership). Super-admins and multi-campus staff profiles must be clearly decoupled from individual institutional rosters to ensure zero orphan or unauthorized cross-tenant records.
12. **Idempotent Offline-First Synchronization & Concurrency Standard (আইডেমপোটেন্ট অফলাইন সিঙ্ক ও কনকারেন্সি নীতি):**
   - **Client-Generated Unique UUIDs:** Every offline-created entity (reports, assessments, attendance records, diary logs) must generate an immutable, collision-resistant unique identifier (e.g. `report_unique_id: "REP-XXXXXXXX"`) at creation time. The backend must use this key for upserting (`get_or_create` / `update_or_create`).
   - **Idempotent API Endpoints:** All synchronization endpoints must be 100% idempotent. If a network blip causes the client sync engine to retry an identical payload multiple times, the server must safely recognize the client unique ID, update the existing record, and return success without creating duplicate rows or altering counters.
   - **Deterministic Conflict Resolution:** Synchronized records must track UTC timestamps (`client_updated_at`, `updated_at`, `edit_time`). When reconciling offline edits with remote database records, the sync engine must resolve conflicts deterministically (last-write-wins by authenticated timestamp or explicit merge diff) rather than blindly overwriting newer changes.
13. **Graceful Fault Tolerance, Safe Defaults & Boundary Isolation (ফল্ট টলারেন্স ও এরর বাউন্ডারি নীতি):**
   - **Module-Level Error Boundaries:** Every major view, complex table, and high-density dashboard widget must be encapsulated within React Error Boundaries. An unexpected null pointer or parse failure within an isolated student row or card must never bring down the entire application or cause a white screen of death.
   - **Defensive Safe Chaining & Non-Destructive Fallbacks:** Never assume deep nested properties or relational keys exist on client records. Always apply optional chaining (`report?.student_details?.name_en`) paired with standardized, non-destructive fallbacks (`—`, `0`, or `[]`).
   - **Zero Silent Data Discarding:** Form validation and submit handlers must never silently discard user input (e.g., dropping mistake/stuck rows if an optional ayah is omitted, or resetting input state without user confirmation). If an input is partially populated, preserve the data with safe fallbacks and notify the user via informative toasts.
14. **Borderless & Soft-Surface Visual Design Evolution (বর্ডারলেস ও স্পষ্ট সফট-সারফেস ডিজাইন নীতি):**
    - **Strict Borderless & Ringless Standard (কোনো বর্ডার ও রিং থাকবে না):** সম্পূর্ণ প্রজেক্টে কার্ড, সেকশন, বাটন, অপশন আইটেম, মেনু ও কনটেইনারে সব ধরনের বর্ডার (`border`, `border-b`, `border-t`, `theme-border`) এবং ফোকাস/সিলেকশন রিং (`ring`, `ring-2`, `ring-[var(--accent-main)]`) সম্পূর্ণ পরিহার করতে হবে (`border-0 ring-0`)। কোনো প্রকার ডার্ক/গাড় বা হার্শ বর্ডার দেওয়া যাবে না। অ্যাক্টিভ/সিলেক্টেড কার্ডেও কোনো বর্ডার বা রিং থাকবে না।
    - **স্পষ্ট ও প্রমিনেন্ট ব্যাকগ্রাউন্ড সারফেস (Distinct Soft-Tinted Surfaces):** বর্ডার দূর করে কার্ড ও অপশন গ্রুপগুলোকে আলাদা করতে স্পষ্ট দৃশ্যমান সফট ব্যাকগ্রাউন্ড সারফেস কালার ব্যবহার করতে হবে।
      - আউটার কনটেইনার: `theme-bg-surface rounded-3xl shadow-xs border-0`
      - ইনঅ্যাক্টিভ অপশন আইটেম: স্পষ্ট দৃশ্যমান সফট ব্যাকগ্রাউন্ড `theme-bg-app hover:theme-bg-elevated/40 border-0` (কখনোই ইনঅ্যাক্টিভ আইটেমে অতিরিক্ত হালকা/অদৃশ্য `theme-bg-sub/80` দেওয়া যাবে না)।
      - সিলেক্টেড/অ্যাক্টিভ কার্ড: স্পষ্ট সফট অ্যাকসেন্ট টিন্ট `bg-[var(--accent-main)]/15 dark:bg-[var(--accent-main)]/25 border-0 ring-0`।
    - **সিলেকশন নির্দেশক হিসেবে শুধুই চেক আইকন ব্যাজ (Pure Check Icon Badge Indicator):** অ্যাক্টিভ কার্ড নির্দেশ করার জন্য কোনো বর্ডার বা রিংয়ের বদলে কেবল একটি পরিচ্ছন্ন বৃত্তাকার ফিল্ড চেক আইকন ব্যাজ (`w-5 h-5 rounded-full theme-bg-accent theme-accent-text flex items-center justify-center shadow-xs shrink-0` সাথে `<CheckIcon className="w-3 h-3" />`) ব্যবহার করতে হবে।
    - **পিকার ও কালার ডটে জিরো বর্ডার (Borderless Color Swatches & Clean Badges):** কালার প্যালেট বা সোয়াচ পিকারের কালার ডটে কোনো প্রকার রিং বা বর্ডার থাকবে না (`w-5 h-5 rounded-full shrink-0 shadow-xs border-0`)। অপ্রয়োজনীয় টেক্সট/টোন ব্যাজ (যেমন `[D]`, `[L]`) সম্পূর্ণ পরিহার করে ইন্টারফেসকে সর্বোচ্চ পরিচ্ছন্ন রাখতে হবে।
    - **Apple & Linear Minimalist Aesthetics:** পর্যাপ্ত ব্রেদিং স্পেস (`space-y-5`, `p-6`), পরিচ্ছন্ন রাউন্ডেড শেপ (`rounded-3xl`, `rounded-2xl`), স্পষ্ট ব্যাকগ্রাউন্ড কনট্রাস্ট ও সাবলীল টাইপোগ্রাফিক হায়ারার্কি নিশ্চিত করতে হবে।
15. **Mandatory Dual-Database Schema Synchronization (উভয় ডেটাবেজে বাধ্যতামূলক যুগপৎ মাইগ্রেশন নীতি):**
    - **Dual-Database Parity:** যখনই কোনো ডেটাবেজ স্কিমা পরিবর্তন করা হবে বা নতুন মাইগ্রেশন তৈরি করা হবে (`makemigrations`), সাথে সাথে **উভয় ডেটাবেজেই** যুগপৎভাবে মাইগ্রেশন রান করতে হবে:
      1. **Local SQLite Engine:** `python backend/manage.py migrate` (লোকাল এনভায়রনমেন্ট সিঙ্কের জন্য)।
      2. **Live Supabase PostgreSQL Engine:** `$env:USE_SQLITE="False"; python backend/manage.py migrate` (লাইভ ক্লাউড ডেটাবেজে সরাসরি স্কিমা আপডেট নিশ্চিত করতে)।
    - **Zero Out-of-Sync Guarantee:** কখনোই শুধু লোকাল ডেটাবেজে মাইগ্রেশন চালিয়ে কাজ শেষ করা যাবে না। প্রতিটি স্কিমা পরিবর্তনে লোকাল SQLite ও লাইভ Supabase PostgreSQL উভয় ডেটাবেজের স্কিমা ১০০% অভিন্ন ও যুগপৎ সিঙ্কে রাখতে হবে।
